# Skill: book-to-skill（书籍→技能包转化）

将一本图书、长篇技术文档或读书笔记，提炼为核心方法论，映射为可执行的工作流步骤，最终生成一份符合 SkillHub 规范的 `SKILL.md` 技能包。

输出是一个可直接放入 `skills/` 目录或 opencode 技能目录的技能文件夹，包含完整的 frontmatter、使用场景说明、分步工作流与参考资料。

## 使用场景

- 读完一本方法论类书籍（管理、工程、设计、沟通等），想把它固化成可复用的 AI 技能
- 手上有长篇技术文档/内部 Wiki，希望提炼为可被 Agent 直接调用的工作流
- 有一堆章节笔记/读书卡片，想结构化成一个统一技能
- 需要将隐性知识显性化，转化为他人也能复用的流程

## 输入要求

支持以下任意一种输入形式（可组合使用）：

| 形式 | 说明 |
|------|------|
| 完整书稿 Markdown / TXT | 全书文本，适合内容完整的经典著作 |
| 目录 + 关键章节 | 只读最有价值的章节，效率高 |
| 读书笔记 / 读书卡片 | 个人理解 + 原文引用混合，适合反思型读者 |
| 已有大纲/思维导图文字版 | 结构化信息，可直接映射步骤 |
| 纯口头描述 | 零散想法，需先补全结构 |

**最佳实践**：输入越结构化，输出越精准。优先提供作者原意（核心论点/方法论框架），其次才是个人感悟。

## 分步工作流

### 第 1 步：理解书籍核心论点

通读输入材料，回答以下问题（在心里或草稿中整理）：

- 这本书要解决什么问题？
- 作者的核心方法论是什么？（模型名、步骤数、关键原则）
- 有哪些可复用的判断标准或决策树？
- 哪些内容只是例子/故事，可以跳过？

**产出物**：一段 200 字以内的「核心论点摘要」，列出方法论名称、步骤数、关键原则。

### 第 2 步：提炼可执行步骤

把方法论拆解为 Agent 可直接执行的步骤序列：

- 每个步骤必须是**动词开头**的可执行动作（如「读取文件」「分析 X」「生成 Y」）
- 步骤之间要有明确的输入/输出依赖关系
- 控制在 **3-8 个步骤**；超过 8 步则分层（主流程 + 子流程）
- 对需要工具调用的步骤，标注具体命令或 MCP 工具名

**产出物**：一个有序步骤列表，每步包含「动作 + 输入 + 输出」。

### 第 3 步：确定触发场景（description 字段）

根据书籍主题和使用频率，写好 `description` frontmatter：

- 第一句说明技能功能
- 补充触发词：用户何时应该调用此技能
- 加入中英文关键词，提高 Agent 命中准确率
- 参考现有技能 description 风格（pushy 一点，多覆盖相关表述）

**产出物**：一句完整的 `description` 文本，100-200 字。

### 第 4 步：撰写 SKILL.md 正文

按以下结构组织正文（参考下方「输出规范」模板）：

1. **角色设定**：Agent 在此技能中扮演什么专家角色
2. **何时使用**：触发条件，与 description 呼应
3. **输入格式**：明确接收什么、不接受什么
4. **工作流**：第 2 步提炼的步骤序列，展开详细说明
5. **输出规范**：生成物的格式要求（如 JSON schema、文件结构）
6. **质量检查清单**：Agent 自检要点，确保输出符合规范
7. **参考资料**：引用原文出处（书名、章节、页码或 URL）

### 第 5 步：组装技能文件夹

在本地创建技能目录：

```
skills/<skill-name>/
├── SKILL.md           # 必填：技能主文档
└── references/        # 可选：参考资料
    └── source-notes.md   # 原始笔记或引用摘录
```

- 技能目录名用 kebab-case（如 `book-to-skill`）
- `SKILL.md` 顶部必须有 YAML frontmatter
- 如有必要，可在 `references/` 放置原文摘录供复核

### 第 6 步：校验生成的技能包

使用仓库内置的校验脚本验证输出是否符合规范：

```bash
python3 skills/book-to-skill/scripts/validate_skill.py skills/<skill-name>
```

- 通过时输出 `OK`（exit 0）
- 失败时逐条列出问题并 exit 1
- 也可将 `templates/SKILL.template.md` 作为骨架参考，确保 frontmatter 占位符与实际字段一致

## 输出规范（SKILL.md 模板）

```markdown
---
name: <skill-name>
version: 1.0.0
description: <功能说明 + 触发场景 + 中英文关键词>
category: 知识转化
tags: [标签1, 标签2, 标签3]
---

# Skill: <技能名称>

<一句话概述技能用途>

## 何时使用

- <触发场景 1>
- <触发场景 2>
- <触发场景 3>

## 输入要求

<明确支持的输入格式，不支持的也说明>

## 工作流

### 第 1 步：<步骤名>
<详细说明 + 示例或命令>

### 第 2 步：<步骤名>
...

## 输出规范

<输出格式要求，如有 schema 请列出>

## 质量检查清单

- [ ] <检查项 1>
- [ ] <检查项 2>
- [ ] <检查项 3>

## 参考资料

- 《<书名>》，<作者>，<章节/页码>
- <其他来源 URL 或引用>
```

## 质量检查清单

Agent 在输出前必须逐条确认：

- [ ] frontmatter 含 `name`、`version`、`description`，且三字段均非空
- [ ] `description` 包含至少 1 个触发场景和 1 个中英文关键词
- [ ] 工作流步骤数在 3-8 之间，每步以动词开头
- [ ] 每个步骤有明确的输入/输出说明
- [ ] 输出规范部分写清了产物格式（Markdown / JSON / 文件结构）
- [ ] 质量检查清单至少包含 3 条可验证的检查项
- [ ] 参考资料引用了原文来源，无凭空编造的章节
- [ ] 全文中文表达流畅，无 AI 腔（避免"综上所述""值得注意的是"等套话）
- [ ] SKILL.md 正文不超过 300 行（过长则拆分 references/）

## 注意事项

- **忠于原著**：方法论应来自原文，不得自行发明作者未提及的概念
- **保持精简**：一本书的方法论不必全搬，挑最可执行的 20%
- **可测试**：工作流步骤应能独立验证，便于后续加 evals
- **命名一致**：技能目录名、frontmatter name、标题三者保持一致
- **风格统一**：参考本仓库内其他技能的 SKILL.md 写法，保持格式一致性

## 失败处理

如果输入材料过于零散（如只有书名无内容、或内容无法提炼出可执行步骤），输出并仅输出：

```json
{"error": "cannot_derive_skill", "reason": "<具体原因>"}
```

并在回复中建议用户补充材料。
