# 集成模式参考

## 决策树

```
通过评估的候选项目：
├─ 只需 1-2 个纯函数 ──► 片段复制（+来源注释+NOTICES）
├─ 库调用、许可证宽松 ──► 依赖引入（锁版本+适配器）
├─ 深度定制、允许传染：
│    ├─ 改动有普适价值 ──► 提 PR 上游（首选）
│    └─ 改动私有 ──► fork + patch 队列
├─ copyleft × 分发软件/SaaS(AGPL) ──► 进程包裹 或 重写
└─ 都不合适 ──► 自研（先写契约测试）
```

## 各模式规范

### 片段复制
1. 文件头：来源 URL + 许可证 + commit hash + 日期
2. 不做无谓重构（小 diff 便于 cherry-pick 上游安全修复）
3. 补最小测试
4. 登记 THIRD-PARTY-NOTICES

### 依赖引入
1. 锁版本（lockfile 入库）
2. 调用点收敛到一个适配器文件
3. 契约测试钉住行为

### fork + patch 队列
- 每个 patch 单一目的；描述写"为什么上游不接受"
- 定期 rebase 上游；冲突清单 = 维护成本清单
- 每个 patch 写"退役条件"（上游官方支持同类功能时删除）
- 复评信号：patch 数 > 20 或 rebase 成本 > 重写成本时重新决策

### 进程包裹
- CLI/容器/RPC 边界最干净；copyleft 一般不跨进程边界
- 定义稳定的接口契约 + 版本协商

### 重写（Clean-room）
- 读文档观察行为 → 关源码 → 自己实现 → 对照行为测试
- 原项目贡献者不得参与（污染风险）
- 算法类独立查专利

## 组合架构（六边形端口-适配器）

```
   业务编排（自研核心）
   ├── 端口A ──► 适配器（开源项目A 的壳）
   └── 端口B ──► 适配器（开源项目B 的壳）
```

三条纪律：
1. 业务代码 import 白名单：只许自己的模块和适配器
2. 适配器暴露**你的**词汇表，不是第三方的
3. 适配器有契约测试，升级依赖跑同一套即知破坏面

## 改进开源四铁律
1. 先跑通它的测试套件再改
2. 新增文件优先于修改老文件
3. 不动上游数据格式/存储布局
4. 每个改动写退役条件
